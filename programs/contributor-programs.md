# Contributor programs

## First Contribution Program

**Purpose:** help a newcomer make one meaningful, reviewable contribution and understand the project.

- Setup instructions that work on a clean machine: [CONTRIBUTING.md](../CONTRIBUTING.md). CI's clean-install job keeps them honest.
- A small set of genuinely beginner-appropriate issues: [good-first-issues.md](good-first-issues.md). Keep 3–5 open at a time.
- Every issue states the **problem, context, expected behavior, files/area, acceptance criteria, test command and maintainer contact**.
- Newcomer checklist:
  - [ ] Read the Code of Conduct
  - [ ] Set up the environment and run `pytest`
  - [ ] Comment on the issue to claim it
  - [ ] Make the change and add a test
  - [ ] Open a PR using the template
  - [ ] Respond to review
- Review promptly when capacity allows. The published expectation is a first response within 7 days, as a target.
- Thank contributors and explain what happened to the contribution (merged, changes requested, or closed with a reason).

## Regular Contributor Program

- Invite people into recurring work only after they show interest and reliable contributions (e.g. 3+ substantive merged contributions).
- Offer ownership of a small subsystem or documentation area, recorded in [ownership.md](../operations/ownership.md) as "contributor-owned".
- Provide design context: link the decision log, and pair on the first design discussion.
- Track contribution quality and collaboration, not raw commit counts.
- **Never promise** jobs, scholarships, admissions benefits or formal credentials.

## Maintainer Development Program

- **Role expectations and decision rights:** [GOVERNANCE.md](../GOVERNANCE.md).
- **Pairing:** each prospective maintainer is paired with an existing maintainer.
- **Start small:** issue triage (Triage permission), then one component.
- **Training topics:** code review (use the PR template as a checklist), releases ([release checklist](../operations/release-checklist.md)), security (a dry run of the disclosure workflow), community conduct (CoC procedures).
- **Permissions** are granted only as needed and reviewed quarterly ([access review](../operations/access-review.md)).
- **Succession:** a backup owner is documented for every critical component.

Appointment is recorded in the decision log and GOVERNANCE.md, with the person's consent.

## Ambassador / community organizer program (later stage)

**Not launched.** It launches only when there is a real community and useful events or material to represent.

When it launches:

- The role is education, local event organization and feedback collection. There are no sales quotas.
- Ambassadors use accurate affiliation statements and disclose that they are volunteers.
- They get a small event kit: the [workshop](workshop/) materials, logo guidance ([brand policy](../policies/brand-and-attribution.md)), and a reporting template.
- They never claim partnerships, endorsements or product capabilities that don't exist.

## Contributor recognition

- Release notes and contributor acknowledgments, **with consent**. Ask in the PR: "May we credit you as @handle in the release notes?"
- Recognize documentation, testing, design, triage and community work, not only code.
- No public ranking by commit count.
- No private personal details are published.
- Any badge, certificate or role has written criteria and never implies accreditation.
